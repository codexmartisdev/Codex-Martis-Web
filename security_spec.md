# Security Specification: Codex Martis Firestore Rules

## 1. Data Invariants
1. **Operator Boundary**: All reads and modifications must be executed by the authenticated operator `codex.martis.dev@gmail.com` with `email_verified == true`.
2. **Project Identity**: Document IDs used by operational collections must be valid sanitized identifiers (`isValidId`: string up to 128 chars, matching `^[a-zA-Z0-9_-]+$`).
3. **Project Integrity**: Projects require `name`, `identifier`, `status`, numeric `progress` between 0 and 100, `createdAt` and `updatedAt`.
4. **Task Integrity**: Tasks require `title`, valid `projectId`, `status`, `priority`, `createdAt` and `updatedAt`.
5. **Environment Integrity**: Environments require `name`, valid `projectId`, `service`, `account` and `status`.
6. **Session Integrity**: Sessions require valid `projectId`, `status`, `objective` and `startedAt`.
7. **History Integrity**: History records require `title`, `category` and `timestamp`.
8. **Project Update Integrity**: Project-update records require valid `projectId`, `schemaVersion`, `createdAt` and `appliedAt`.
9. **Payload Bounds**: User-controlled text fields have explicit size limits to reduce accidental or malicious oversized writes.
10. **Temporal Consistency**: Core operational entities store creation/update timestamps as strings generated by the application; security rules require those fields where the domain model marks them as mandatory.
11. **Seed Safety**: Automatic Firestore seed is disabled in production unless `NEXT_PUBLIC_ALLOW_FIRESTORE_SEED=true` is explicitly set for an intentional migration.
12. **Catch-All Default Deny**: Any path outside explicit collection matches is denied by default.

## 2. Persistence Failure Contract
Firestore write helpers must never convert a failed remote write into a resolved Promise. They must:

1. Record structured diagnostic context through `handleFirestoreError`.
2. Re-throw the original Firebase error to the caller.
3. Allow the store/UI layer to decide whether to retry, roll back optimistic state, or surface an error.
4. Never mark a manual seed/synchronization as successful when seeding is disabled or the batch write failed.

## 3. The "Dirty Dozen" Malicious Payloads
1. **D1: Unauthenticated Creation**: An unauthenticated user attempts to create a project document directly in `/projects/{projectId}`. Expected: `PERMISSION_DENIED`.
2. **D2: ID Poisoning**: An attacker tries to write using an oversized or malformed document ID containing script characters. Expected: `PERMISSION_DENIED`.
3. **D3: Negative Progress Injection**: An attacker attempts to set `progress: -50` on a project. Expected: `PERMISSION_DENIED`.
4. **D4: Exorbitant Progress Range**: An attacker attempts to set `progress: 9999` on a project. Expected: `PERMISSION_DENIED`.
5. **D5: Missing Required Project Fields**: Creating/updating a project without `name`, `identifier`, `status`, `progress`, `createdAt` or `updatedAt`. Expected: `PERMISSION_DENIED`.
6. **D6: Invalid Task Relationship**: Creating a task without a valid `projectId`, or without `priority`, `createdAt` or `updatedAt`. Expected: `PERMISSION_DENIED`.
7. **D7: Oversized String Attack**: Writing an oversized text payload to bounded fields such as `description`, `objective`, `observations` or serialized update JSON. Expected: `PERMISSION_DENIED`.
8. **D8: Unverified Email Write**: Writing with an unverified email token (`email_verified == false`). Expected: `PERMISSION_DENIED`.
9. **D9: Session Missing Objective/Start**: Writing a session without `objective` or `startedAt`. Expected: `PERMISSION_DENIED`.
10. **D10: Environment Missing Service/Account**: Creating an environment without `service`, `account` or `status`. Expected: `PERMISSION_DENIED`.
11. **D11: Rogue Collection Write**: Attempting to write to arbitrary path `/system_configs/master_key`. Expected: `PERMISSION_DENIED`.
12. **D12: Malformed Audit Records**: Writing a history event without `title`, `category` or `timestamp`, or a project update without `appliedAt`. Expected: `PERMISSION_DENIED`.
